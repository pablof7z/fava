## Criterion 1 — The open sequence · **PASS**

**Authority.** `ARCHITECTURE.md:3014-3017`:

> `fava-observe` owns:
> `source boundary -> initial evaluation -> handle release -> later updates`

`GOALS:313` (QUERY-004): *"The initial query value MUST be produced from the configured local query sources without waiting for any relay response."* Acceptance `GOALS:325`: *"with every relay unreachable, opening a query returns its local view or a local-source error, never hangs waiting for the network."*

**Code.** `crates/fava-observe/src/observer.rs:162`:

```rust
pub fn open(&self, query: Query) -> Result<Observation, ObserveError>
```

Not `async`. There is no `.await` anywhere in `Observer::open`, `evaluate_initial`, `retain`, `start_engine`, or `routes::bind` — the compiler enforces this, so it is not a property that can regress by inattention. The facade door `crates/fava/src/lib.rs:112-114` is `async` only to keep the public signature stable and its body is one non-awaiting call, annotated as such at `:104-107`.

**Ordering as executed** (`observer.rs:162-255`): engine start (idempotent, `OnceLock`, spawns only the reconciler) → event-cache source open `:168` → write-store source open `:175` → route binding `:188` → initial evaluation `:200` → registry install `:211` → demand retained `:214` → evidence decorated and published `:223-229` → projection task spawned `:230` → **handle returned** `:248`. That is exactly `ARCH:3017`.

**Relay work is enqueued, not awaited.** `registry.assign` (`registry.rs:131-137`) bumps a watch revision; the reconciliation owner wakes on it (`engine.rs:139-152`) on its own task. Every provider call is issued from `operations.rs` on a spawned, cancellable task and reports back through a bounded channel (`engine.rs:46,62-71`). No provider future is polled on the opening thread.

**Falsifiers.** `explicit_live.rs:25` (`relay_establishment_does_not_delay_the_coherent_local_observation`) holds establishment on the transport and wraps `fava.observe` in a 50ms timeout; `open_sequence.rs:20` does the same at owner level; `shared_work.rs:209` proves a stalled relay does not delay a reachable one. **M1 confirms these are real gates** — inserting a 200ms await into `Fava::observe` turns three of them red.

**Residual caveat (recorded, not a failure of this criterion).** `Router::open` and `RouterSession::current` (`crates/fava-routing/src/lib.rs:337,347`) are **synchronous** trait methods called inline by `routes::bind` (`routes.rs:78-80`) with no deadline. There is no *future* to await, so SC-1's literal wording holds — but a router that blocks rather than returns will block the handle, and no falsifier covers that. A *refusing* router is already absorbed: `chain.rs:70-86` records a bounded error per router and continues instead of aborting the chain.

## Criterion 4 — Shared work · **PASS**

**Authority.** `GOALS:296`: *"Equivalent observations MAY share local evaluation, relay connections, and wire subscriptions. Distinct source authority, relay access, freshness, or presentation-relevant evidence MUST NOT be erased merely because the event filters are equal."* Acceptance `GOALS:298`: *"two equivalent handles share work; closing one does not close work still needed by the other."*

**Distinctness is structural.** `registry.rs:163-178` (`desired`) — documented *"never deduplicated"* — walks every installed observation and pushes each one's `RelayDemand` verbatim. Identity is `DemandId { owner, branch }` (`demand.rs:14-20`), never derived from the filter. The planner contract forbids the owner from pre-merging: `SubscriptionPlanError::DuplicateDemand` (`planner.rs:107`) exists precisely so a caller that collapses two demands into one id is refused.

**Two observations, identical filters, different acquisition.** `shared_work.rs:86` (`an_explicit_and_an_automatic_observation_of_one_filter_stay_distinct`) opens one explicit and one automatic query over the same relay and asserts `demand[0].filter == demand[1].filter` **and** `demand[0].id() != demand[1].id()`, then that the evidence reports `RouteOrigin::Explicit` for one and `RouteOrigin::Automatic{..}` for the other, while `dials == 1`. That is exactly the GOALS:296 sentence, and `shared_work.rs:129` adds the close-safety half: withdrawing the automatic route leaves the explicit observation's relay untouched.

**The refcount is on the wire subscription.** `InstalledSubscription.serves: BTreeSet<DemandId>` (`installed.rs:24`) is the attribution fan-out of one REQ. `Slot::orphaned` (`slot.rs:89-96`) reports a subscription closable only when **every** `DemandId` it serves has left. `attach::surviving_owners` (`attach.rs:84-108`) recomputes owners as `still-requested ∪ newly-attached`, and `diff::withdrawals` (`diff.rs:90-116`) closes only entries absent from that map. `validate_plan` CR-1 (`conformance.rs:46-75`) rejects any plan that closes a subscription still serving a requested demand, whatever planner produced it. This is separate from — and layered above — the *connection* refcount, which is the transport's `RelaySessionLease` (`fava-transport/src/lease.rs:27-32`).

**Discrimination.** M2 — collapsing filter-equal demand inside `Registry::desired` — turns four `shared_work.rs` falsifiers red. Note that it turns **zero** `explicit_live.rs` falsifiers red: the facade-level suite alone cannot see demand collapse, only the owner-level suite can.

`explicit_live.rs:139-153` closes the *duplicate* of a merged demand and asserts the REQ list is byte-identical and no CLOSE was sent, then closes the *last* demand for one author and asserts the survivor keeps its over-broad filter. A refcount keyed on observation count instead of served demand would send a CLOSE at the first close and fail.

## Criterion 5 — The admission window · **PASS WITH GAPS**

**Fixed 10ms.** `admission.rs:28`:

```rust
pub(crate) const ADMISSION_WINDOW: Duration = Duration::from_millis(10);
```

matching the planner contract's own statement of the caller's obligation (`planner.rs:66-68`: *"a **fixed 10ms, first-arrival-anchored** deadline; later arrivals join the cohort and **never extend** it"*).

**First-arrival-anchored and non-sliding — in the code.** `engine.rs:195-205`: the window is armed only when `slot.uncovered(&demand)` is non-empty, and `if slot.armed { continue; }` refuses to arm a second timer while one is pending. `operations::arm_admission` (`operations.rs:83-95`) sleeps exactly `window` from the moment it was armed. `flush` clears `armed` at `engine.rs:334`.

**A running request is never rewritten — on join.** Post-freeze arrivals take one of two paths and neither touches the wire: `Engine::attach` (`engine.rs:215-269`) is explicitly *"a refcount edit, not wire work: the subscription keeps its exact id and its exact filters, and no plan is computed"*; otherwise the demand is `uncovered` and opens its **own** request beside the incumbent. Inside the planner, `attach::admit` (`attach.rs:34-52`) removes covered demand *before* `grouping::group` ever sees it, and `grouping.rs:7-10` states that installed subscriptions never enter grouping.

**A running request is never rewritten — on withdrawal.** `diff.rs:84-89`: *"A subscription that keeps an owner is retained unchanged, even when it is now broader than what its remaining owners asked for."* Enforced provider-independently by CR-1.

**Falsifiers, and what they would catch.** `explicit_live.rs:97` proves that losing one of two identical demands emits no CLOSE and that losing the last demand for one author leaves the merged filter intact. `explicit_live.rs:161` and `shared_work.rs:396` prove a post-window arrival opens a second REQ while `after[0] == installed` and `withdrawals` stays empty. **M3** confirms these are load-bearing: planning against an empty incumbent namespace turns two of them red.

**What no falsifier catches — the blind spot.** **M4**: deleting the `if slot.armed { continue; }` guard, so every new uncovered demand re-arms and the window *slides*, leaves **all 28 falsifiers green**. Every existing test opens its observations back-to-back inside a single scheduler turn, so a sliding deadline and a fixed one behave identically. The starvation failure the fixed anchor exists to prevent — a steady arrival stream postponing the first REQ indefinitely — is asserted nowhere.

**One documentation defect found here.** `engine.rs:9-11` and `lib.rs` claim the cohort is *"compiled by the planner **against an empty incumbent namespace**"*. It is not: `engine.rs:345,352` passes the real `slot.installed`. The property the prose is reaching for is true, but it is enforced *inside* the planner (`attach.rs` filters before `grouping.rs`), not by the owner passing an empty set — and M3 shows that actually passing an empty set breaks two falsifiers. The comment describes a design the code deliberately does not implement.

## Criterion 6 — GOALS:426 (QUERY-010) · **FAIL**

**Authority.** `GOALS:426`: *"Reopening dropped demand MUST use fresh request identity so a late EOSE or event from the old request cannot settle the new one."* Acceptance `GOALS:428`: *"dropping and quickly reopening a request cannot inherit the old request's in-flight completion."*

**Identity is not derived from filter content — that half holds.** `crates/fava-subscriptions-standard/src/wire.rs:32-34`:

```rust
pub(crate) fn mint(revision: PlanRevision, ordinal: usize) -> SubscriptionId {
    SubscriptionId::new(format!("{PREFIX}-{}-{ordinal}", revision.0))
}
```

Nothing filter-derived, nothing relay-advertised. `wire.rs:1-15` argues the case explicitly. A repo-wide search finds no other `SubscriptionId` minting site in production code.

**But the freshness half fails.** `PlanRevision` is stored **per `Slot`** (`slot.rs:30`), and `Slot::new` starts it at `PlanRevision(0)` (`slot.rs:48`). `Slot::advance` — the reconnect path — deliberately preserves it (`slot.rs:62-72`, *"The plan revision keeps climbing: an id minted for a closed request must never come back"*). **`Engine::release` does not**: `completions.rs:325` is `let Some(mut slot) = self.slots.remove(relay)`, which drops the counter with the slot. When demand for that relay later returns, `Engine::establish` (`engine.rs:275-278`) recreates it with `Slot::new` and the next plan mints `fava-1-0` again.

This directly violates the obligation the planner contract places on its caller, `planner.rs:46-49`:

> **Fresh revision.** `revision` is strictly greater for every plan whose content could differ from the last, and is never reused within one transport session. Wire identity is minted from it, so a reused revision can hand a reopened subscription the identity of a closed one — which `GOALS:426` (QUERY-010) forbids by name.

**Reachability.** The reuse is only harmful if the *socket* survives the drain, and it does whenever another lease holder is present: `fava-transport-websocket/src/lib.rs:60-85` reuses one socket per `RelaySessionKey` and only closes it on `ReleaseOutcome::Closed`, i.e. when the last holder leaves. The standard assembly hands publication **the same `Arc<dyn Transport>`** (`crates/fava/src/builder.rs:206-235`), and `fava-publisher-nip01/src/lib.rs:53-56` acquires a real lease on the relay session key and holds it across the whole publish attempt including the OK-wait.

**Demonstration** (disposable probe, run and deleted). One outsider lease on `wss://retained.example`; open an observation, wait for its REQ, close it, wait for the CLOSE, confirm the socket is still held, then open a second observation on the same relay:

```
FIRST  = fava-1-0
SECOND = fava-1-0
same socket dials = 1
```

Same live socket, no reconnect, and the reopened request carries the identity of the request just CLOSEd on it. A late EOSE or EVENT for the first request settles the second. That is the exact scenario `GOALS:428` names.

**Why the existing evidence misses it.** There *is* a strong QUERY-010 falsifier — `crates/fava/tests/multi_relay.rs:275`, `reconnect_uses_fresh_identity_and_rejects_old_subscription_frames` — which drives the public facade and asserts `assert_ne!(replacement, subscription, "the replayed request must not reuse the retired wire id")` plus that a frame naming the retired id is refused. It passes, and it is a good test. But it exercises the **reconnect** path, which is exactly the path where `Slot::advance` *preserves* the counter. The **drop-and-reopen** path named by the acceptance line has no falsifier at all. A second control probe confirmed the negative case: closing and reopening within one scheduler turn, before the reconciler processes the withdrawal, yields `fava-1-0` then `fava-2-0` — correct — which is why the defect is invisible to anyone testing the obvious ordering.

**Fix shape.** Hoist the plan-revision counter out of `Slot` into `Engine` (keyed by relay, surviving slot release) or into the transport session identity, so it is monotone for the lifetime of the socket rather than the lifetime of the slot.

### Gaps Summary

The architecture the phase set out to restore **is** in the tree. `Observer::open` is a synchronous total function, so relay-blocking on open is not merely absent but unrepresentable. The facade's relay layer is gone with no compatibility path, and the 20 new crate-private nominals in `fava-observe` were audited individually — `Slot` is the nearest analogue to `OpenedRelay` and differs on every axis that made `OpenedRelay` misplaced. Demand distinctness, wire-subscription refcounting, and the never-rewrite-a-running-REQ rule are all real, all enforced provider-independently by `validate_plan`, and all demonstrably gated by falsifiers that go red under deliberate mutation. That is a materially different situation from the six milestones this remediation exists to revoke.

Three things stop this being a pass.

**One demonstrated correctness defect.** `GOALS:426`'s acceptance clause is false today: the plan-revision counter lives inside `Slot`, `Engine::release` drops the `Slot`, and a relay whose observe-side demand drains and returns while a publication lease keeps the socket alive mints the wire id of the request it just closed. The probe shows `fava-1-0` twice on one socket with `dials=1`. The existing QUERY-010 falsifier covers reconnect — the one path where the counter *is* preserved — so the corpus is structured such that this specific defect could not have been caught.

**One invariant with no evidence.** The fixed, first-arrival-anchored window is correct in code and invisible to the tests: making it slide leaves all 28 green.

**One gate that now lies.** `architecture.yml` still declares three falsifiers expected-red until 07.6 and excludes them from the gating workspace run. Two of them now pass and the third no longer exists under that name. The phase changed the behaviour the gate encoded and left the gate behind — which is a smaller instance of exactly the failure mode Phase 07.9 was created to address.

Separately recorded but not phase-scope failures: the derived-query dependency graph (`ARCH:2068`) is owned by nobody and unmapped corpus-wide; a facade-owned, unjoinable observation task survives in `query_source.rs`; source-scoped evidence is partly reconstructed by string-matching a stringified transport reason; and the containment predicate is implemented twice, in two crates, with an existing behavioural disagreement.
