# Phase 07.1: Universal Publication Vocabulary and Typed NIP-02 Reads — Specification

**Created:** 2026-08-22
**Ambiguity score:** 0.11 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

An application can read, discover, edit, publish, and await NIP-02 contact-list changes through the README-level typed Rust API, while the same universal `publish`/`by`/`to` vocabulary accepts every write payload without exposing `WriteIntent` ceremony.

## Background

Phase 7 delivered authorless `ReplaceableEventEdit` values, deterministic rebasing, and the narrow `fava-nip02::{follow, unfollow, materializer}` tracer. The generic exact tag-filter axis required for `followers_of` has since landed on `main`. The crate README records the intended application experience, but its typed reads, discovery builders, richer follow helper, string conversion, and direct publication examples are not implemented.

The facade still accepts an application-constructed `WriteIntent` and returns `AcceptedWrite`. The settled Whiteboard design instead makes publication synchronous local acceptance through `fava.publish(payload)`, with optional `fava.by(signer)` and `fava.to(relays)` scope handles, returning an awaitable `Write`. Local issues 0014 and 0015 describe that vocabulary and are incorporated into this phase rather than deferred.

NIP-02 contact lists are shared documents. Implementations can place malformed or duplicate `p` rows, unknown tags, and legacy relay JSON in `content`. A Fava edit must expose evidence it cannot interpret and preserve data it does not own.

## Requirements

1. **Universal synchronous publication door**: Applications publish an accepted Fava write payload directly, without constructing a `WriteIntent`.
   - Current: `Fava::publish` accepts `WriteIntent` and returns `AcceptedWrite`; ordinary callers must name engine-internal intent/routing vocabulary.
   - Target: `Fava::publish(payload) -> Result<Write, PublishError>` synchronously performs durable local acceptance. Automatic routing is the default, and accepted materialization is query-visible before relay contact. `WriteIntent` and `WritePayload` remain engine-internal cross-crate vocabulary and are not re-exported by the `fava` facade.
   - Acceptance: Public Rust examples compile for a replaceable edit, unsigned event, and presigned event through `fava.publish(...)`; tests prove the call returns after local acceptance without waiting for router or network progress and matching observations already contain the accepted result.

2. **Typed signer and relay scopes**: Applications can narrow a publication with inert `PublishAs` and `PublishTo` handles before supplying its payload.
   - Current: Signer and explicit routing choices require intent construction; invalid signer scoping is not excluded by the publication door's type shape.
   - Target: `fava.by(key)` selects an available signer for replaceable edits only; `fava.to(relays)` selects explicit destinations for every payload; either order composes. Both handles are `#[must_use]`, borrow `Fava`, and cause no work until `publish`. Explicit relays are normalized by relay identity, retain first-occurrence order, reject an empty set, and retain the configured upper bound.
   - Acceptance: Compile-pass coverage includes `fava.by(carol).publish(edit)`, `fava.to([r1, r2]).publish(payload)`, and both composed orders. Compile-fail coverage proves signer scoping cannot publish unsigned or presigned events. Runtime tests prove dropped scopes create no store row, receipt, provider call, or acquisition work; empty relay input is refused before work; `[r1, r2, r1]` becomes `[r1, r2]`.

3. **Awaitable write settlement**: The value returned by publication owns receipt inspection and bounded waiting for caller-selected delivery sufficiency.
   - Current: Callers receive `AcceptedWrite` and use facade-level terminal waiting; the application-facing value does not express `settled(all())`, `settled(at_least(n))`, or a receipt predicate.
   - Target: `Write` exposes stable write/receipt identity, the current receipt, and `settled(predicate)`. `all()` and `at_least(n)` are standard predicates; custom `Fn(&Receipt) -> bool` predicates are allowed. `at_least(0)` is a typed refusal, not immediate success. Waiting resolves when the predicate succeeds or when the receipt becomes terminal, returning a terminal `NotReached` error carrying the receipt when the threshold was not met. Receipt facts retain mixed outcomes and derived acknowledged, rejected, and desired counts.
   - Acceptance: Deterministic tests prove success at the exact requested threshold, refusal of zero, reevaluation on receipt changes, terminal `NotReached` without a hang, and preservation of per-destination mixed outcomes in both successful and failed returns.

4. **Ownership and dependency boundary**: Publication vocabulary is universal and protocol crates remain protocol-pure.
   - Current: The NIP-02 README depends on publication ergonomics that do not yet exist, creating a temptation to special-case kind 3 or move publication concerns into `fava-nip02`.
   - Target: The `fava` facade owns `publish`, `by`, `to`, `PublishAs`, `PublishTo`, and application-facing `Write`; neutral write/publication owners retain custody, receipt, routing, signer, and observation lifecycles. `fava-nip02` owns only kind-3 values, parsing, query construction, and edits, and depends on neutral contracts rather than the engine facade or providers.
   - Acceptance: Dependency and source checks find no NIP-02-specific kind switch in universal owners and no signer, publication, receipt, store, runtime, socket, or provider lifecycle owned by `fava-nip02`; another write payload uses the same publication door without changing its protocol crate.

5. **Typed contact-list decoding with complete evidence**: Kind-3 events decode once into an author-scoped `ContactList` without hiding rows the crate cannot safely interpret.
   - Current: Applications must inspect raw tags; `ContactList`, typed `Follow` accessors, and row-level malformed/duplicate evidence are absent.
   - Target: A valid kind-3 event decodes into a `ContactList` exposing its author, first-occurrence-ordered valid follows, and typed evidence for every malformed or later duplicate `p` row. An empty list is valid. Invalid public keys and relay hints are row evidence rather than whole-list failure. Petnames preserve their original UTF-8 bytes without normalization. Non-kind-3 or otherwise invalid event input is refused by the list decoder.
   - Acceptance: Tests cover empty, one-row, multi-row, malformed-key, malformed-relay, duplicate-target, non-kind-3, and mixed-validity events; every input `p` row is accounted for as either one valid first occurrence or typed evidence, with no silent omission.

6. **Typed NIP-02 reads and discovery**: Applications obtain contact lists and social-graph discovery through ordinary Fava queries and pure projections.
   - Current: No `contact_list`, `follows_of`, or `followers_of` API exists, although exact generic tag filtering is available.
   - Target: `contact_list(author or authors)` returns the replaceable kind-3 query for the concrete author set; `follows_of(snapshot)` projects typed public keys from parsed lists; `followers_of(subject)` returns a kind-3 query using the generic exact `p`-tag axis. Query acquisition, observation, cache, and provenance remain ordinary Fava behavior.
   - Acceptance: Public API tests prove single- and multi-author contact-list queries, newest replaceable results, first-hop and second-hop composition, follower discovery using exact `#p`, empty inputs/results, stable ordering, repeated projection, and concurrent independent observations.

7. **Complete NIP-02 edit helpers with lossless preservation**: The README write surface edits only understood contact rows and preserves the rest of the shared document.
   - Current: `follow(PublicKey)` and `unfollow(PublicKey)` exist; `follow_with`, string conversion, and the complete preservation contract are not exposed as the documented public surface.
   - Target: `follow`, `unfollow`, and `follow_with` accept fallible public-key inputs including hex strings and return `ReplaceableEventEdit`. `follow_with` can supply an optional relay hint and petname. Adding an already-followed target preserves the first existing matching `p` row verbatim, including its relay hint, petname, and extra columns, and does not replace it with requested metadata. Later matching duplicates are removed as typed duplicate evidence permits; unfollow removes every matching `p` row. All foreign or unknown tags—including one-column tags and tags such as `["t", "nostr"]`—and legacy kind-3 `content` are preserved byte-for-byte and in their original relative order.
   - Acceptance: Tests prove string and key inputs, metadata encoding, inverse semantics, deterministic rebase, idempotent repeated add/remove, existing-target preservation, duplicate cleanup, bounds/refusals, and byte-for-byte preservation and ordering of unknown tags and content across follow and unfollow.

8. **README-driven Rust and live-relay proof**: The crate README is both the DX North Star and an executable claim backed by controlled integration evidence.
   - Current: The README explicitly labels most of its API and publication examples as a broader unimplemented target; existing tests prove only the Phase 7 tracer locally.
   - Target: `crates/fava-nip02/README.md` describes only the delivered surface, its application examples compile, and a controlled live-relay canary proves publish, observation, typed readback, and settlement through the public Rust API. No Swift or Kotlin wrapper is required in this phase.
   - Acceptance: README examples are compiled or mirrored by public-API tests; the crate/unit/workspace validation passes; a repeatable controlled-relay test follows, observes, decodes, and settles a kind-3 write without private engine calls.

9. **Authoritative vocabulary and documentation**: The adopted publication and NIP-02 nouns replace superseded public documentation in one approved architecture change.
   - Current: Issues 0014/0015 are still marked proposed, authoritative specs name the old facade door, the vocabulary registry lacks parts of the settled surface, and the README contains delivered-versus-target migration narration.
   - Target: Authoritative specs and `docs/internals/vocabulary.toml` describe the current `publish`/`by`/`to`/`Write` and typed NIP-02 model only; approved public nouns have owners, lifecycles, distinctions, forcing requirements, and executable falsifiers. Superseded facade vocabulary, proposed labels, compatibility aliases, and target-status narration are removed rather than retained as parallel history.
   - Acceptance: `python3 tools/check_vocabulary.py` and its unit tests pass; repository searches find no application-facing `WriteIntent` publication example or facade compatibility alias; the README has no unimplemented-status disclaimer for this phase's surface.

## Boundaries

**In scope:**
- Issues 0014 and 0015: the complete universal publication door and its approved public vocabulary.
- Synchronous local acceptance, signer and relay scope handles, returned `Write`, receipt predicates, and settlement behavior.
- The complete `fava-nip02` README target: typed decoding, row evidence, query builders, discovery, `follow_with`, string conversion, and direct publication.
- Lossless preservation of foreign tags and legacy content while editing understood matching `p` rows.
- Rust public API, unit/compile/integration evidence, and a controlled live-relay canary.
- Updates to authoritative specifications, vocabulary, focused issues, and the crate README required to describe only the delivered model.

**Out of scope:**
- `fava-simple-groups` behavior or its README implementation — Phase 07.1.1 consumes this phase's shared publication/query foundation.
- Reactive `ValueSet` or another live derived-set abstraction — discovery remains ordinary queries plus pure projection.
- Swift and Kotlin wrapper parity — this phase locks and proves the Rust vocabulary first.
- Runtime-handle capture from issue 0016 — independent runtime ownership concern.
- Refusing publication at build time when no router chain is configured from issue 0017 — independent assembly-validity concern.
- Replacing query routing collections with a shared non-empty collection type — this phase changes explicit publication routing only where required by `to(...)`.
- NIP-29 protocol behavior, group state, or per-host group truth — owned by Phase 07.1.1.

## Constraints

- The authority order in repository `AGENTS.md` applies; behavior and ownership must agree with the four complete specifications before the partial API semantics document.
- This phase is the focused architecture change approving its new public nouns; the feature implementation cannot invent additional vocabulary. Every public or cross-crate nominal type must pass the registry's seven-part approval and executable falsifier.
- `publish` is synchronous durable local acceptance. Network acquisition, routing progress, acknowledgement, and settlement cannot delay its return.
- Replaceable edits remain authorless until acceptance; the chosen signer author is resolved once and frozen into accepted custody. Signer scoping of unsigned or presigned events must remain unrepresentable.
- Explicit relay input is bounded, empty is refused before work, duplicates normalize by identity, and first-occurrence order is authoritative.
- Protocol crates are engine-free and provider-free. Universal owners consume neutral contracts and must not branch on NIP-02 kind semantics.
- Event/tag byte bounds and tag-count bounds are typed refusals, never truncation. Externally supplied predicate waiting terminates with receipt terminality.
- Valid follow rows retain first-occurrence order. Invalid keys, invalid relay hints, and later duplicate targets remain typed evidence. Petnames are not Unicode-normalized.
- Editing a shared kind-3 document may remove or replace only understood matching `p` rows. Unknown tags, unknown columns on the preserved first matching row, and legacy content retain bytes and relative order.
- Existing concurrent worktrees, especially the dirty M8 worktree, are not modified, reset, rebased, or used as an implementation base.

## Acceptance Criteria

- [ ] `fava.publish(edit)?`, `fava.publish(unsigned)?`, and `fava.publish(presigned)?` synchronously return `Write` after durable local acceptance and before network work.
- [ ] `fava.by(carol).to([r1, r2]).publish(edit)?` and `fava.to([r1, r2]).by(carol).publish(edit)?` compile and freeze the selected author and destinations at acceptance.
- [ ] Signer-scoped publication of unsigned or presigned events fails to compile; dropping either scope handle is inert.
- [ ] Empty explicit relay input is refused before custody or provider work; duplicate relays are deduplicated by identity in first-occurrence order; upper bounds are enforced without truncation.
- [ ] `Write::settled(all())`, `Write::settled(at_least(n))`, and custom receipt predicates resolve at the correct receipt revision; `at_least(0)` is refused.
- [ ] Terminal settlement without predicate satisfaction returns `NotReached` with the terminal receipt, including all mixed per-destination outcomes and derived counts.
- [ ] A kind-3 event decodes to typed ordered follows plus typed evidence accounting for every malformed or duplicate `p` row; an empty list succeeds.
- [ ] Invalid public keys and relay hints remain row evidence; petname bytes are returned without normalization; invalid event-level input is refused.
- [ ] `contact_list`, `follows_of`, and `followers_of` compile through the documented public Rust API and use ordinary query/observation/provenance behavior.
- [ ] `followers_of(subject)` uses the generic exact `p`-tag filter and excludes events without that exact target.
- [ ] `follow`, `unfollow`, and `follow_with` accept public keys and supported strings; metadata and inverse behavior match the README.
- [ ] Following an existing target preserves the first matching `p` row verbatim and removes later duplicates; unfollow removes all matching `p` rows.
- [ ] Follow and unfollow preserve every foreign/unknown tag and legacy content byte-for-byte and preserve their relative order.
- [ ] Source qualification, deterministic rebasing, idempotency, size/tag bounds, and typed refusal behavior remain valid under concurrent source arrival.
- [ ] The README examples compile and a controlled live-relay canary proves public publish → observe → typed decode → settlement.
- [ ] `fava-nip02` owns no signer, router, publication, receipt, store, runtime, socket, acquisition, or observation lifecycle.
- [ ] Authoritative specs, focused issues, README, and vocabulary registry describe only the delivered model; no facade compatibility alias preserves the old publication door.
- [ ] `python3 tools/check_vocabulary.py`, its unit tests, focused crate tests, public API/compile tests, and relevant workspace checks pass.
