## Summary

The first fix iteration closes the original facade compatibility doors, surfaces reservation-release failure, makes initial route application part of acceptance, binds recovered explicit routes to exact public relay lanes, adds bidirectional event-level old-data checks, bounds NIP-02 formatting, and returns the facade below 500 lines. Four shipping blockers remain: terminal redb acceptance can create a database that refuses restart; idempotent atomic acceptance compares only part of the initial route; the old-data identities and completion claims are outside the artifact seal; and uppercase NIP-19 secret keys evade the retained-secret scan. Two evidence/cohesion defects also remain.

The retained pair at `apps/canary/runs/phase-07.1-pair.nrSPUU` verifies. Its phase-owned child processes are absent and ports are closed; unrelated PID 75649 predates the phase and is excluded as instructed. Focused atomic-acceptance, terminal-retention, old-data, and manifest-negative tests pass, as do the vocabulary checker and its unit tests, but the causal gaps below are not exercised by those tests.

## Critical Issues

### CR-01 [BLOCKER]: A terminal redb receipt with a source cannot survive restart

**File:** `crates/fava-write-store-redb/src/semantic.rs:126-148`, `crates/fava-write-store-redb/src/validation.rs:198-206`, and `crates/fava-write-store-redb/tests/semantic_write_store/admission.rs:132-165`

**Issue:** Initial route application can make a newly applied edit terminal before commit. The store then deliberately omits semantic custody with `(!terminal).then_some(&custody)`, even when `selected_source` populated `publication.revision_source`. On reopen, durable validation rejects every receipt that has `revision_source` but no semantic custody. The new terminal-retention test passes only `source = None`, so it cannot expose this self-created invalid durable state. A settled `NoDestination` or otherwise terminal edit applied from an existing kind-3 event therefore succeeds and is query-visible, but makes `RedbWriteStore::open` fail after restart.

**Fix:** Separate retained terminal provenance from active semantic custody, or persist enough bounded provenance for validation without putting terminal receipts back into active recovery. Add a redb restart test that accepts an initial terminal route with `Some(&source)`, closes and reopens the store, proves the receipt remains readable, and proves `recover_applied_edits()` remains empty.

### CR-02 [BLOCKER]: Idempotent atomic acceptance treats materially different route plans as equal

**File:** `crates/fava-write-store-memory/src/semantic.rs:125-145,435-439` and `crates/fava-write-store-redb/src/semantic.rs:61-83,384-388`

**Issue:** Both stores use `route_matches` to decide whether an already-owned semantic edit is an exact idempotent retry. That predicate compares only revision, settlement, and destination keys. It ignores `RoutePlan::shortfalls` and settled-absent coverage, even though `apply_route_to_receipt` persists both as `receipt.route_shortfalls`. Two initial plans with the same revision/destinations/settlement but different failure evidence therefore return the first accepted write as success instead of refusing the non-identical mutation. The caller cannot tell that its second atomic acceptance fact was discarded, violating exact operation identity and attributable failure evidence.

**Fix:** Compare the complete persisted effect of the candidate plan: derive its bounded desired destinations and route-shortfall evidence with the same neutral helper used for application, then require exact equality with the receipt's revision, settled state, destinations, and shortfalls. Add provider-parity tests in memory and redb where only a shortfall or settled-absent coverage reason changes; the second acceptance must refuse and must not consume or rewrite the first receipt's facts beyond the documented reservation consumption.

### CR-03 [BLOCKER]: The seal does not cover the identities and completion facts used as old-data proof

**File:** `apps/canary/src/croissant_nip02_evidence.rs:58-104`, `apps/canary/src/croissant_nip02.rs:462-507`, and `apps/canary/src/croissant_nip02.rs:533-570`

**Issue:** `artifact_seal` signs only the digest of `artifact_sha256`. `manifest.json` is explicitly outside that hash set, yet the pair verifier takes `group_id`, all three event IDs, write/receipt identities, terminal result, bounds, teardown, and completion booleans directly from the mutable manifest. `validate_manifest` checks their shapes but does not cross-check them against sealed `flow.json`/`evidence.jsonl` facts. A manifest can therefore replace the four cross-run identity needles with fresh strings, or alter terminal/completion claims, without changing any sealed artifact or invalidating the signature. This was reproduced against a temporary copy of the retained pair: replacing all four identity fields and the terminal outcome in both manifests still produced `verified Croissant NIP-02 pair`. The verifier scans meaningless replacement values and accepts a pair that has not proved bidirectional old-data exclusion.

**Fix:** Include a canonical digest of every verification claim in the author-signed seal, or derive and cross-check every manifest claim from the sealed artifacts before using it. Add causal negative tests that mutate one identity and one terminal/completion fact without changing the artifacts or seal and require the verifier to reject specifically because the signed evidence no longer agrees.

### CR-04 [BLOCKER]: Uppercase NIP-19 secret keys evade the retained-secret scan

**File:** `apps/canary/src/croissant_nip02_evidence.rs:16-44`

**Issue:** The derived-key scan includes raw bytes, lowercase and uppercase hex, and the lowercase `nsec` returned by `to_bech32`. It does not include the consistently uppercase NIP-19 representation. Bech32 accepts consistently upper- or lowercase encodings, so a valid `NSEC...` private key retained in a log or artifact is a supported encoded secret form that passes both scans. The manifest's nine scan classes overclaim the private-key redaction proof.

**Fix:** Add uppercase `nsec` needles for both author and target keys and list those exact classes in `SECRET_SCAN_CLASSES`; cover any accepted URI-wrapped forms through the same canonical variant inventory. Add direct unit tests over `assert_secrets_absent` for raw, lower/upper hex, and lower/upper NIP-19 forms so each encoding fails because of the scanner itself.

## Warnings

### WR-01 [WARNING]: The derived-secret negative is satisfied by a stale signature, not the secret scanner

**File:** `apps/canary/src/croissant_nip02_tests.rs:97-109`

**Issue:** The test injects the derived hex secret and refreshes `artifact_sha256`, but it does not regenerate `artifact_seal`. `validate_manifest` verifies the seal after the hashes, so the test rejects on the stale signed digest even if `secret_needles` and `assert_secrets_absent` are deleted. The pair verifier cannot derive the erased seed itself, and this test does not causally prove either generation-time secret scan.

**Fix:** Unit-test `assert_secrets_absent` directly with every derived representation and assert the exact redacted refusal. For end-to-end generation, add a test hook that injects one secret before each pre-/post-manifest scan and prove the corresponding scan rejects; do not use post-hoc seal mismatch as the secret-scan witness.

### WR-02 [WARNING]: The redb semantic owner crossed the soft limit without a cohesion rationale

**File:** `crates/fava-write-store-redb/src/semantic.rs:1`

**Issue:** The atomic-acceptance fixes grew this file to 527 lines. `AGENTS.md` requires a concrete cohesion reason above the 500-line soft limit. The recorded exception covers the memory semantic owner and redb recovery suite, not this production module; earlier phase summaries instead claim changed production modules remain below 500 lines.

**Fix:** Split a cohesive acceptance/validation owner into a private module, or record a concrete repository-visible ownership rationale explaining why that split would weaken cohesion. Keep the existing 800-line hard limit and add the same measured source guard used for the facade if the intended rule is to remain below 500.
