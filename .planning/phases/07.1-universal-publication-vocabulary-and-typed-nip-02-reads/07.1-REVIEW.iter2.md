# Phase 07.1: Code Review Report

**Reviewed:** 2026-08-22T03:22:58Z
**Depth:** standard
**Files Reviewed:** 85
**Status:** issues_found

## Summary

The phase has six shipping blockers: two neutral-contract compatibility seams remain public on the facade; publication silently discards store failures; redb recovery does not bind explicit routes to their durable delivery lanes; the retained-pair verifier does not prove event-level old-data exclusion; its secret scan cannot detect derived private keys; and NIP-02 helpers allocate attacker-sized strings before applying their advertised bounds. Two evidence/cohesion defects should also be fixed.

The retained sign-off pair currently verifies, and independent probes found both phase-owned PIDs absent and both ports closed. PID 75649 predates this phase and was excluded as instructed.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01 [BLOCKER]: The facade still exposes neutral custody vocabulary and a second acceptance door

**File:** `crates/fava/src/lib.rs:108` and `crates/fava/src/lib.rs:251-254`

**Issue:** `Fava::accept_event` remains public and returns `fava_write_store::AcceptedWrite`; `Fava::preview_write_routes` remains public and requires `fava_write::WriteIntent`. This directly contradicts the adopted authority that applications use one `publish`/`by`/`to` door, do not receive `AcceptedWrite`, and do not construct `WriteIntent`. Removing only re-exports does not remove these callable public signatures. The source-inventory test at `crates/fava/tests/facade_surface.rs:20-56` misses both methods, so the claimed compatibility prohibition passes while the incompatible surface remains usable.

**Fix:** Remove or make both methods non-application-visible. Move direct acceptance/neutral route preview to their owning provider contracts, or redesign preview over the adopted inert payload scopes. Extend `facade_has_no_write_intent_compatibility_door` to inspect public method signatures and compile-fail external calls to `accept_event` and `preview_write_routes`.

### CR-02 [BLOCKER]: Publication discards store failures and can leak capacity or strand settlement

**File:** `crates/fava-publication/src/lib.rs:98-124`

**Issue:** When semantic preparation fails, `release_active(reservation)` is ignored. A replaceable store is permitted to fail; hiding that failure can leave a durable capacity reservation leaked while the caller receives an unrelated preparation error. After acceptance, the initial automatic `apply_route` result is also ignored. If that mutation fails, `publish` still returns a `Write` whose receipt can remain open without the selected route or an attributable shortfall, so `settled(...)` may wait forever. Both violate failure isolation and the rule that every failure remains scoped and attributable.

**Fix:** Make reservation release failure part of the returned typed error (preserving the original cause as context). Do not discard post-accept route failure: atomically install the prepared initial route with acceptance, or commit a bounded terminal/shortfall fact to the accepted receipt before returning its `Write`. Add a faulting `WriteStore` test for each mutation and assert no leaked reservation and bounded settlement.

### CR-03 [BLOCKER]: Redb recovery accepts explicit routes whose durable lanes target different relays

**File:** `crates/fava-write-store-redb/src/validation.rs:57-68` and `crates/fava-write-store-redb/src/validation.rs:95-115`

**Issue:** Reconstruction validates only that an explicit route is non-empty, unique, and bounded. It never proves that `publication.destinations` and `desired_destinations` are the public relay-session keys derived from that exact ordered route. A corrupted row can therefore persist `routing = [r1, r2]` while retaining a desired lane for `r3`; recovery accepts it and the publication runner drives the stored lane, potentially sending an event to an undeclared relay or omitting a declared one. This defeats ordered-route custody and creates a data-disclosure risk.

**Fix:** For `WriteRouting::Explicit`, derive the expected `RelaySessionKey::new(relay, RelayAccess::public())` set from the ordered relay vector and require exact equality with the retained destination keys/desired destinations according to the terminal-state contract. Add recovery mutations for missing, extra, and substituted lanes, not only empty/duplicate route vectors.

### CR-04 [BLOCKER]: Pair verification self-asserts old-data exclusion and checks only group strings

**File:** `apps/canary/src/croissant_nip02.rs:459-463` and `apps/canary/src/croissant_nip02.rs:510-529`

**Issue:** Each run writes `old_data_excluded: true` unconditionally. The pair verifier trusts that boolean and scans the opposite run only for `group_id`; it does not scan or actively query for the opposite `group_event_id`, `baseline_event_id`, or final `event_id`, despite the phase contract requiring run two to exclude run-one group/event data. A pair containing the other run's event bytes but not its group text can pass.

**Fix:** Derive this fact from evidence instead of writing a literal. Before teardown, query the second relay for every first-run event/group coordinate expected absent, or make the verifier scan both directions for all cross-run group and event identifiers and validate an explicit negative-query artifact. Reject the pair unless those exact negative witnesses pass.

### CR-05 [BLOCKER]: The canary cannot detect retained derived private keys

**File:** `apps/canary/src/lib.rs:378-383` and `apps/canary/src/croissant_nip02.rs:437,656-680`

**Issue:** Author and target private keys are deterministic SHA-256-derived values distinct from the raw scenario seed. The pre-manifest scan checks only the raw seed bytes; the verifier checks forbidden JSON key names, not values or artifact bytes representing the derived secret key. A log/artifact containing the actual private key under an innocuous field passes `secret_scan_passed` and pair verification. The manifest therefore overclaims the required private-key redaction proof.

**Fix:** While the seed is still in process memory, derive the exact author and target secret representations and scan every artifact for raw bytes, hex, and any supported encoded secret form as well as the input seed. Run the scan again after manifest creation, record which secret classes were checked without recording their values, and add a negative test injecting a derived secret into an already-hashed artifact with hashes refreshed.

### CR-06 [BLOCKER]: Public NIP-02 helpers allocate unbounded input before typed refusal

**File:** `crates/fava-nip02/src/edit.rs:26-64` and `crates/fava-nip02/src/edit.rs:212-214`

**Issue:** The public helpers advertise bounded, typed refusal, but `impl ToString` forces an unbounded allocation before key parsing and `follow_with` clones the entire petname before its encoded-length check. A hostile `Display` implementation or very large string/petname can exhaust memory or panic the process before `WriteIntentError::TooLarge` is possible. This violates the repository boundedness gate for externally influenced input.

**Fix:** Format targets through a capped `fmt::Write` sink (or another existing bounded conversion) so allocation stops at the maximum accepted key representation, then parse. Check petname byte length and the total encoded length before `to_owned`. Add tests with over-bound target and petname inputs that prove refusal occurs without constructing an over-bound owned buffer.

## Warnings

### WR-01 [WARNING]: The old-data negative test is satisfied by hash mismatch, not the old-data check

**File:** `apps/canary/src/croissant_nip02_tests.rs:86-91`

**Issue:** The test adds an unlisted file after manifest sealing. `validate_manifest` runs artifact-hash verification before the cross-run group scan, so the verifier rejects on the changed hash set even if the old-data logic is deleted. The test cannot falsify CR-04's missing event/group exclusion behavior.

**Fix:** Recompute the mutated run's artifact hash map before invoking the verifier, or unit-test the cross-run exclusion function directly. Cover group ID, group event ID, baseline event ID, and final event ID independently.

### WR-02 [WARNING]: The facade root crossed the repository soft limit without a cohesion rationale

**File:** `crates/fava/src/lib.rs:505`

**Issue:** This phase grew the file from 465 to 505 lines. `AGENTS.md` requires a concrete cohesion reason for every code file above 500 lines; unlike the 505-line memory semantic owner and 742-line canary boundary, no rationale is recorded for this file. This makes the public facade root continue accumulating unrelated assembly, query, publication, preview, and error responsibilities.

**Fix:** Split a cohesive owner such as builder/build errors or route preview into a private module, or record a concrete repository-visible cohesion rationale and a measured reason that the split would weaken ownership.
