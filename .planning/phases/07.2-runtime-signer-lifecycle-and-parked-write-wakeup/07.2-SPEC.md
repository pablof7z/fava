# Phase 07.2: Runtime Signer Lifecycle and Parked-Write Wakeup — Specification

**Created:** 2026-08-23
**Ambiguity score:** 0.03 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

A running Fava instance can add, explicitly replace, and remove bounded signer
attachments, and an already accepted unsigned write reacts only to changes for its exact
event pubkey without engine rebuild or write-identity loss.

## Background

`FavaBuilder` currently accepts signers, and `fava-publication::Publication::new` copies
them into an immutable `BTreeMap<PublicKey, Arc<dyn Signer>>`. The publication loop checks
that map once when a materialization opens. If no signer is present, the write remains
unsigned and no runtime signal can retry it. The authoritative architecture already assigns
runtime signer registration and availability to `fava-session`; that crate and lifecycle
owner do not yet exist.

## Requirements

1. **Runtime attachment (`SESSION-01`)**: The same running Fava instance accepts a signer after build without replacing the engine, session, write store, or accepted write identity.
   - Current: Builder-supplied signers are frozen into publication at construction.
   - Target: Builder signers seed one runtime `Session`, and `Fava::add_signer` mutates that same session after build.
   - Acceptance: A write accepted with no Alice signer retains the same `WriteId` and `ReceiptId`, then signs and continues after `fava.add_signer(alice_signer)` without rebuilding Fava.

2. **Exact wakeup (`SESSION-02`)**: A signer attachment change affects only unsigned work whose exact event pubkey has a different current attachment generation.
   - Current: There is no session-change signal or wakeup path.
   - Target: Publication observes a coalescible session revision, reloads its own event pubkey, and starts or restarts signing only when that exact attachment generation changed.
   - Acceptance: Adding or replacing Bob's signer does not start, cancel, or restart Alice's signer operation; adding Alice's signer wakes every open Alice write exactly once for the installed generation.

3. **Explicit duplicate and replacement semantics (`SESSION-03`)**: Add refuses an already attached pubkey without mutation, while replacement is a separate explicit operation.
   - Current: Duplicate builder signers fail publication construction; no runtime mutation exists.
   - Target: `add_signer` returns `SessionError::DuplicateSigner`; `replace_signer` returns `SessionError::MissingSigner` when no attachment exists and otherwise installs one fresh generation.
   - Acceptance: Repeating add for one pubkey leaves the original signer current; explicit replacement makes only the replacement current and signals exactly one committed revision.

4. **Removal and re-add (`SESSION-04`)**: Removal preserves durable accepted-write and receipt state while detaching one signer generation and cancelling its current publication operation.
   - Current: Signers cannot be removed without rebuilding Fava.
   - Target: `remove_signer(pubkey)` refuses a missing attachment, invalidates the removed generation, and matching unsigned work remains awaiting a signer until add installs a fresh generation.
   - Acceptance: Removing Alice during a blocked sign leaves the same accepted write and receipt open; the blocked completion is inert, and re-adding Alice signs that same current materialization.

5. **Stale completion isolation (`SESSION-05`)**: A signer completion may install signed state only when both its materialization identity and exact session attachment generation remain current.
   - Current: Store installation checks materialization and event identity but cannot distinguish two signer attachments for the same pubkey.
   - Target: Publication captures the attachment generation, re-checks it before installation, and treats replaced/removed generation completions as inert.
   - Acceptance: Releasing an old signer after replacement or removal cannot install an event, record a refusal against the fresh signer, or start any delivery lane; retired materialization completion remains equally inert.

6. **Bounded attachment (`SESSION-06`)**: Session holds at most 64 exact pubkey attachments and every refused mutation is atomic.
   - Current: Builder signer collection is not explicitly bounded before publication indexing.
   - Target: Empty and one-signer sessions are valid; the 64th distinct pubkey succeeds; the 65th returns `SessionError::SignerCapacityExceeded { limit: 64 }`; replacement at capacity remains valid because cardinality does not grow.
   - Acceptance: Boundary tests cover 0, 1, 64, and 65 distinct signers, duplicate keys, replacement at capacity, and concurrent attempts at the final slot with no partial mutation or cardinality overflow.

7. **Single owner and lock isolation (`SESSION-07`)**: `fava-session` is the only mutable signer-attachment owner, while publication owns signer operations and the write store owns accepted writes.
   - Current: Publication owns the immutable signer map directly.
   - Target: Publication depends on `fava-session`; session mutation and lookup are short synchronous critical sections; `Signer::availability` and `Signer::sign_event` run after all session/publication locks and write-store transactions are released.
   - Acceptance: Dependency checks find no publication-owned signer map or reverse session dependency, and a blocking signer cannot block unrelated session mutation, receipt reads, or another pubkey's signing lifecycle.

## Boundaries

**In scope:**

- New `fava-session` contract/owner crate using existing `PublicKey` and `Signer` values.
- Runtime `Fava::add_signer`, `Fava::replace_signer`, and `Fava::remove_signer` facade operations.
- Builder-supplied signer seeding through the same runtime session.
- Exact attachment generations, bounded mutation, coalescible change notification, and publication wakeup.
- Cancellation and inert rejection of replaced, removed, and retired-generation signer completions.
- Public facade, owning-component, dependency, deliberate-break, recovery, and lock-isolation evidence.

**Out of scope:**

- `fava.by(signer)` convenience — `by(PublicKey)` remains unchanged and signer conversion is unrelated to attachment lifecycle.
- Multiple simultaneous signers or fallback selection for one pubkey — one exact attachment keeps policy deterministic.
- Current-account selection, login/logout UX, session import/export, and account aliases — later account-session slices own those behaviors.
- NIP-46, hardware, browser-extension, Swift, Kotlin, or platform signer implementations — this phase uses the existing replaceable signer contract.
- Raw private-key or `nsec` input — applications remain responsible for constructing signer providers.
- Any second write, receipt, retry, routing, delivery, or persistence lifecycle in `fava-session`.

## Constraints

- No new external crate dependency; `fava-session` may depend only on existing workspace contracts and synchronization/error crates already used by the repository.
- One signer per exact `PublicKey`; no implicit sole-signer or current-account fallback.
- The attachment limit is exactly 64; no silent eviction, truncation, or replacement through add.
- Session change delivery may coalesce revisions, but publication must reload current exact state so no final attachment is missed.
- Every attachment generation and change revision uses checked monotonic identity and returns typed refusal on exhaustion.
- Provider calls occur outside owner locks, publication locks, and write-store transactions.
- Existing durable write/recovery semantics and the public `by(PublicKey)` author scope remain unchanged.

## Acceptance Criteria

- [ ] The owning `fava-session` tests first fail without runtime mutation, then pass for empty, add, duplicate add, explicit replace, remove, missing replace/remove, and 0/1/64/65 capacity boundaries.
- [ ] Concurrent final-slot additions linearize to one success and one typed capacity refusal; the session never exceeds 64 attachments.
- [ ] A public Fava test accepts an Alice write before any signer exists, adds Alice at runtime, and observes the same `WriteId`/`ReceiptId` sign and continue without rebuild.
- [ ] Adding, replacing, or removing Bob's signer neither invokes nor cancels Alice's signer; adding Alice wakes all and only currently open Alice materializations.
- [ ] Duplicate add leaves the original attachment active; explicit replacement invalidates it and starts at most one operation for the fresh generation.
- [ ] Removal during a blocked signer operation leaves the write and receipt open; the old completion is inert; re-add signs the same current materialization.
- [ ] An old signer completion released after replacement cannot install signed state, record refusal against the fresh generation, or create delivery work.
- [ ] A completion for a retired materialization generation remains inert under the existing materialization checks.
- [ ] Builder-supplied signers seed the same `Session` and duplicate/capacity failures surface as build refusal before Fava is returned.
- [ ] Blocking `availability` or `sign_event` behavior cannot hold a session/publication lock or write-store transaction and cannot block mutation or another pubkey's work.
- [ ] Dependency checks prove `fava-publication -> fava-session -> fava-signer/fava-write`, no reverse edge, and no publication-owned mutable signer map.
- [ ] The deliberate break that suppresses session-change handling fails add-after-acceptance evidence, and the break that ignores attachment generation fails stale-completion evidence.
- [ ] Vocabulary checks and unit tests pass except for any separately demonstrated pre-existing baseline finding; `git diff --check`, targeted Cargo tests, workspace tests, Clippy, and Bazel tests pass.
- [ ] No `by(signer)` overload, signer wrapper, current-account fallback, raw-secret input, or second session-owned publication lifecycle is introduced.
