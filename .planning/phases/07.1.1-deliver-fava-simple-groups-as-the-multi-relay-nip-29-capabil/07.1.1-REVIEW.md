## Narrative Findings (AI reviewer)

## Summary

The pure capability and neutral relay-authority paths preserve host-qualified evidence and avoid a group-specific runtime. The blocking defects are in the claimed independent canary proof: its verifier authenticates producer-written claims without deriving those claims from the retained evidence, does not cover all cross-run event identities, and accepts an unbounded, symlink-following filesystem tree. Two additional robustness defects affect hostile saved-edit bytes and cancellation-safe child reaping.

## Critical Issues

### CR-01: The independent verifier does not derive flow claims from retained evidence

**Classification:** BLOCKER  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence.rs:59-139`  
**Issue:** `validate_manifest` verifies the manifest's artifact hashes and author seal, then validates only the manifest's own scalar/array claims. It never parses `flow.json`, `children/processes.json`, or either wire log to recompute shared/unique provenance, relay-local metadata/admin disagreement, exact custom-event handoffs, invalid-context zero frames, observation CLOSE frames, or teardown correspondence. The seal is produced by the same run that writes the claims, so it proves integrity after signing, not that the claims are supported by the hashed artifacts. A producer can write passing arrays/counts, hash arbitrary contradictory artifacts, reseal the manifest with its run author, and the purported independent verifier accepts it. This directly invalidates Plan 12's independent-evidence exit gate.

**Fix:** Parse each retained semantic artifact and recompute every completion claim. Compare `flow.json` exactly with the manifest, compare `children/processes.json` with `ready`/`teardown`, parse bounded complete JSONL frames to derive event IDs, serving relay evidence, handoffs, refusal zero-frame facts, and CLOSE facts, and reject any claim that is not independently derivable before accepting the seal.

### CR-02: Cross-run exclusion omits both unique event IDs

**Classification:** BLOCKER  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence.rs:249-293`  
**Issue:** `verify_pair_identity` compares `shared_event_id` and `custom_event_id` between runs but never compares either value in `unique_event_ids`. `reject_cross_run_data` likewise scans only `group_id`, `shared_event_id`, and `custom_event_id`. Two manifests may therefore reuse one or both per-host unique events, or one run may retain the other run's unique event bytes, while the verifier reports a distinct, contamination-free pair. This contradicts the recorded requirement for distinct event identities and bidirectional old-data exclusion.

**Fix:** Build the complete per-run identity set, including both `unique_event_ids`, and require the two event-ID sets to be disjoint. Scan each bounded artifact tree for every other-run event identity, not only the shared/custom subset. Add resealed mutation cases for cross-run reuse and retained cross-run bytes for each unique ID.

### CR-03: The public evidence verifier follows symlinks and has no input-size bounds

**Classification:** BLOCKER  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence_support.rs:56-85`  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence_support.rs:103-118`  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence.rs:25-39`  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups_evidence.rs:372-394`  
**Issue:** The CLI accepts a caller-selected evidence directory. `collect_files` uses `Path::is_dir`/`is_file`, which follows nested symlinks, recursively descends without a depth or entry bound, and converts paths lossily. Callers then repeatedly read whole files into memory; the manifest itself is also read without a byte limit before JSON decoding. A nested symlink can escape the selected root or form a recursion cycle, and a large/deep tree can exhaust stack, memory, or time. The verifier therefore violates both path containment and the repository's explicit hostile-input boundedness gate.

**Fix:** Walk with `symlink_metadata`/`DirEntry::file_type`, reject every symlink and non-regular file, preserve validated UTF-8 relative paths, and enforce explicit maximum depth, file count, per-file bytes, aggregate bytes, and manifest JSON bytes. Stream hashing/searching through bounded buffers and verify canonical containment before every open. Add symlink-escape, cycle, depth+1, count+1, file-size+1, and aggregate-size+1 refusal tests.

## Warnings

### WR-01: The saved-list materializer accepts non-canonical duplicate hosts

**Classification:** WARNING  
**File:** `/Users/pablo/Work/fava/crates/fava-simple-groups/src/edit.rs:269-290`  
**File:** `/Users/pablo/Work/fava/crates/fava-simple-groups/src/edit.rs:371-410`  
**Issue:** `ReplaceableEventEdit::new` is public and accepts opaque change bytes, while `SavedListMaterializer::supports` accepts any edit decoded by `Input::group`. That decoder validates host count and URL syntax but not host uniqueness. For a save/rename with no matching source row, `apply_group` filters against an unchanged `found` set while appending, so two identical encoded hosts produce two identical saved rows. Capability constructors happen to encode normalized `Group` hosts, but the public materializer boundary accepts hostile/recovered edit bytes and promises deterministic, idempotent surgery.

**Fix:** Enforce canonical first-occurrence host uniqueness during decode, preferably refusing duplicate-host encodings in `supports` and `materialize`. As defense in depth, update the append loop's seen set as each row is emitted. Add a directly constructed duplicate-host `ReplaceableEventEdit` test for both absent and existing source rows.

### WR-02: Two-child supervision is not cancellation- or panic-safe

**Classification:** WARNING  
**File:** `/Users/pablo/Work/fava/apps/canary/src/croissant_simple_groups.rs:238-290`  
**Issue:** After both children start, `supervise_owned_pair` awaits the caller-supplied flow directly and performs both `stop().await` calls only after that future returns normally. If the supervising future is cancelled or the flow panics, control never reaches either cleanup call. Tokio's child `kill_on_drop` can request termination, but it does not produce the required exact teardown facts and is not an awaited reap. Thus the summary's “always reaped” claim is proven only for `Ok`, ordinary `Err`, and second-child startup failure, not for cancellation/panic at this ownership boundary.

**Fix:** Put each child behind a cancellation-safe owner task/guard that always terminates and awaits its exact child, and have the supervisor collect both teardown results on normal return, error, panic, and cancellation. Add controlled panic and task-abort tests that assert both exact PIDs are absent/reaped, both ports are closed, and no unrelated PID is touched.
