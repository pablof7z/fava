# Phase 06.1: Code Review Report

## Summary

The literal tag-value representation, exact cell-one matching, wire projection, and one-axis planner merge are consistent, but the evaluator has two observable correctness defects. A current local replacement can fail to shadow a cached predecessor when the successor does not satisfy the query, and newest-first ordering contradicts its public event-ID tie-break contract. Three additional gaps weaken the canary, vocabulary gate, and query-identity tests. No security vulnerability was found in the scoped files.

Focused Cargo tests for query identity, source merge, wire conversion, grouping, and the public facade all passed, as did the vocabulary checker and its unit tests; those passes do not exercise the counterexamples below.

## Narrative Findings (AI reviewer)

### Critical Issues

#### CR-01: Selection is applied before replaceable-winner resolution

**Classification:** BLOCKER  
**File:** `crates/fava-query-standard/src/lib.rs:31-49`  
**Issue:** `evaluate` filters each event by selection and authority before grouping candidates by `EventCoordinate`. If an older cached replaceable event has the requested tag but a newer current local materialization at the same coordinate does not, the local successor is discarded first and the cached predecessor is returned. This violates QUERY-005's requirement that the current local materialization shadow its cached predecessor until cancellation. The same ordering can resurrect a cached predecessor under `only_from_relays` when the newer local winner lacks qualifying relay evidence.

**Fix:** Resolve the deterministic winner for every coordinate before applying query selection and result authority, then filter only the winner set. Add a regression with an older cached replacement carrying the requested tag and a newer local replacement omitting it; the result must be empty until the local write is cancelled.

```rust
let mut by_coordinate = BTreeMap::<EventCoordinate, EventRecord>::new();
for record in by_id.into_values() {
    let coordinate = record
        .event
        .coordinate()
        .map_err(|_| QueryEvaluationError::MissingEventId)?;
    match by_coordinate.entry(coordinate) {
        std::collections::btree_map::Entry::Vacant(entry) => {
            entry.insert(record);
        }
        std::collections::btree_map::Entry::Occupied(mut entry) => {
            if record_is_newer(&record, entry.get()) {
                entry.insert(record);
            }
        }
    }
}

let mut events: Vec<_> = by_coordinate
    .into_values()
    .filter(|record| {
        matches_selection(query.selection(), record)
            && matches_authority(query.source().authority(), record)
    })
    .collect();
```

#### CR-02: Newest-first uses the oldest-first event-ID tie break

**Classification:** BLOCKER  
**File:** `crates/fava-query-standard/src/lib.rs:52-60`  
**Issue:** `QueryOrdering::NewestFirst` is publicly documented as timestamp descending and then greatest event ID, but the tie clause uses `left.id().cmp(&right.id())`, which places the least ID first. Both ordering modes therefore use least-ID-first for equal timestamps. Applications receive an order that contradicts `fava-query/src/lib.rs:82-86`, and a whole-query limit can select the wrong record at the boundary.

**Fix:** Reverse the ID comparator only for newest-first and add equal-timestamp tests for both orderings, including a limit of one.

```rust
QueryOrdering::NewestFirst => right
    .created_at()
    .cmp(&left.created_at())
    .then_with(|| right.id().cmp(&left.id())),
QueryOrdering::OldestFirst => left
    .created_at()
    .cmp(&right.created_at())
    .then_with(|| left.id().cmp(&right.id())),
```

### Warnings

#### WR-01: The real-relay witness verifies REQ counts, not the grouped filter

**Classification:** WARNING  
**File:** `apps/canary/src/grouping.rs:414-462`  
**Issue:** `verify_wire` only recognizes payloads by the `["REQ"` prefix and counts them per connection. It never parses the grouped REQ or checks that its filter contains the exact case-sensitive tag key and all 300 values. An over-broad grouped filter could fetch the whole relay corpus, pass ingest against that same over-broad attribution, and still produce exact per-query results after local refiltering. The canary would report exact wire equivalence despite failing to prove it.

**Fix:** Parse every client-to-relay REQ payload, identify the one-request grouped connection, and assert its single filter has exactly the expected `#d` value set and no unintended axes. On the no-grouping side, assert the multiset of 300 serialized filters equals the 300 logical demands, not only that 300 REQs were observed.

#### WR-02: Temporary-path suppression can hide a real vocabulary violation

**Classification:** WARNING  
**File:** `tools/check_vocabulary.py:180-183`  
**Issue:** A discovered crate token is skipped whenever the same line contains `/tmp/` followed by that token anywhere. A specification line can therefore contain an ordinary unregistered crate reference plus a temporary evidence path using the same text and evade the closed-vocabulary gate. The check needs to classify each regex occurrence by its own position, not search the entire line.

**Fix:** Iterate with `SPEC_CRATE.finditer`, and suppress only a match whose immediately preceding characters identify it as the first component of a temporary path. Add a test where an ordinary crate reference and a matching temporary path occur on the same line; the ordinary occurrence must still be rejected.

```python
for match in SPEC_CRATE.finditer(line):
    prefix = line[max(0, match.start() - len("/tmp/")) : match.start()]
    if prefix != "/tmp/":
        crates.add(match.group(1))
```

#### WR-03: Query identity tests assume unequal values cannot hash-collide

**Classification:** WARNING  
**File:** `crates/fava-query/tests/query_identity.rs:53-54`  
**Issue:** The case-sensitivity test, and again the absent-versus-empty test at lines 101-102, require unequal queries to produce unequal `DefaultHasher` outputs. Rust's `Hash` contract guarantees equal values hash equally; it does not guarantee unequal values never collide. These assertions can fail after a hasher implementation change even when query identity remains correct.

**Fix:** Keep `assert_ne!` on the `Query` values and keep hash equality assertions for equivalent constructions. Remove hash-inequality assertions for non-equivalent values, or test the exact canonical selection fields instead.
