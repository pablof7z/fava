# Phase 07.8 Context

**Source:** `.planning/audit/2026-08-23/LEDGER.md` Wave 5, plus

## Decision taken by Pablo — router acquisition

Routers acquire through a trait the engine implements. One capability: open a
query. The trait refuses anything that is not `QueryAcquisition::Explicit` or
`Freshness::CacheOnly`. That refusal is the entire recursion guard.

Reasons the router does not receive the concrete `Fava`:

- It would confer `publish`, `cancel_write`, `close`, `reset`, and
  `preview_routes`. A router must not be able to publish an event or shut down
  the engine. The narrowing is about capability.
- `Observer` holds `Vec<Arc<dyn Router>>`. A router storing `Arc<Fava>` is a
  reference cycle that leaks the engine.
- A third-party router linking `fava` would work with that engine only and could
  not be tested without constructing one.

## The binding constraint on implementation

**The query must run through the exact same code path as an application query.**
Same `Observer::open`, same admission window, same subscription grouping, same
transport session acquisition, same ingest, same evidence, same cancellation.
There is no router-specific machinery anywhere below the trait method.

The trait method is a capability restriction and a delegation. Nothing else.

**If executing a router query requires any change to the execution path, stop and
report it.** That is a signal the path has an assumption it should not have, and
the finding matters more than the feature. Do not add a branch, a flag, a
parameter, or a special case to make a router query work. Do not duplicate a
code path "for routers".

## Verified facts from RESEARCH.md — do not re-derive

- The guard is Explicit **or** CacheOnly. `cache_only()` leaves acquisition at
  `Automatic` (`observer.rs:188` gates on `if live`), so a predicate demanding
  `Explicit` alone rejects the cache read the outbox needs.
- Since 07.6, `Observer::open` is synchronous and total. Router recursion is
  therefore a synchronous cycle ending in stack overflow, and `chain.rs:141`'s
  `catch_unwind` does not catch it.
- The handle passes at `open()` time and is not stored by the router.
- Coalescing needs no router-side work: the registry keeps demands distinct, the
  10 ms admission cohort groups them, and `serves` refcounting releases on last
  withdrawal.
- `Fava::preview_routes` and `publish(WriteRouting::Automatic)` reach routing
  without issuing a query, so an acquisition-mode constraint has no jurisdiction
  over them. They are not on the trait; confirm they remain unreachable from a
  router.

acquisition is explicitly routed. This prevents automatic-routing recursion."
