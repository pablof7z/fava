# Phase 07.8 Plan 01: Settled Absence Requires an Answer — Summary

A router that failed can no longer be read as a router that answered "I cover nothing", so a
refused `open()` leaves an automatic write `Open` with an attributed shortfall instead of
settling it terminal `NoDestination`.

## The defect

`Composer::new` seeded every configured router with `RouteContribution::default()`, and
`complete_targets` filled any request target no contribution mentioned with
`CoverageState::SettledAbsent`. Those two facts compose into a false positive: a router whose
`open()` returned `Err(RouterError::Refused)` kept its default slot, contributed nothing, and was
indistinguishable from a router that answered absence. `plan.settled` became `true`,
`receipt.route_settled` followed it (`crates/fava-write-store/src/receipt.rs:164`), and
`settle_route` turned an empty desired-destination set into `ReceiptOutcome::NoDestination` — a
terminal reason no router ever produced.

## What changed

`crates/fava-routing/src/chain.rs` only.

- `Composer` carries `answered: Vec<bool>`, one slot per configured router, initialised to `false`.
- `Composer::accept` sets the slot when — and only when — the contribution is retained. When the
  bounds check rolls the contribution back, the previous flag is restored, so a router that had
  already contributed coherently keeps its answer and a router whose first contribution was
  over-bound does not gain one.
- The flag is never cleared. `chain.rs:78`, `:83`, `:329` and `:333` (refusal at open, refusal
  reading the current contribution, a later incoherent contribution, and session end) all leave it
  untouched, which is exactly right: a router that ends after a coherent contribution keeps that
  contribution and therefore keeps its answer.
- `complete_targets` takes the all-answered fact. An unmentioned target settles absent only when
  every configured router answered and the target is not already outstanding; otherwise it is
  written to the coverage map as `Unresolved` **and** inserted into the contribution's unresolved
  set.
- `Composer::merged` passes `all_answered()`. `Composer::upstream_plan(index, _)` passes
  `index >= self.contributions.len() && self.all_answered()`, which is always `false` from inside
  the chain loop — routers from `index` onward have not been asked, so an upstream view can never
  claim settled absence.

Zero-router chains are unaffected: `[].iter().all(..)` is vacuously true, so an empty chain still
settles absent.

## Bounds

The unresolved set now grows to the same cardinality `coverage` already carried.
`validate_contribution` bounds the two at the same magnitude (`MAX_TARGETS * factor` and
`MAX_COVERAGE * factor`, both 256 x the factor). Both bounds were left exactly as they were.
`combined_bound_overflow_is_a_shortfall_not_a_spawned_panic` still passes unchanged.

## Stop condition: did not trigger

The plan's stop condition was that resolving the receipt transition must not require editing
`fava-publication` — that would mean settlement has two producers. It does not.
`settle_route` derives `ReceiptOutcome` from `receipt.route_settled` alone, which is assigned from
`plan.settled` at `crates/fava-write-store/src/receipt.rs:164`. Changing what `plan.settled` means
in the routing owner changed the receipt transition with no edit under `crates/fava-publication/`
or `crates/fava-write-store/`. **Settlement has exactly one producer, and it is the routing
owner.** The LEDGER's WRITE-027 cross-owner question
(`.planning/audit/2026-08-23/LEDGER.md:373-390`) is closed by the routing owner alone.
