<objective>
Introduce the contract through which a router acquires its own inputs, and implement it on the
engine. One capability: open a query. The implementation refuses anything that is neither
`QueryAcquisition::Explicit` nor `Freshness::CacheOnly`. That refusal is the entire recursion
guard.

Purpose: `07.8-CONTEXT.md` records Pablo's ruling that routers acquire through a trait the engine
implements, not through the concrete `Fava` — because `Fava` would confer `publish`, `cancel_write`,
`close`, `reset`, and `preview_routes`, because `Observer` holds `Vec<Arc<dyn Router>>` and a
stored engine reference is an unbreakable cycle, and because a third-party router linking `fava`
could not be tested without constructing an engine.

Output: the contract in `fava-routing`, its first real implementation on `Observer`, and the
falsifiers for the guard. The `Router` trait signature change and the four call sites are plan 03.

## THE BINDING CONSTRAINT

A router query runs the **exact same code path** as an application query: same `Observer::open`,
same admission window, same subscription grouping, same transport session acquisition, same
ingest, same evidence, same cancellation. The trait method is a capability restriction and a
delegation. Nothing else.

**Stop condition.** If executing a router query turns out to require a branch, a flag, a new
parameter, or a duplicated path *below* the trait method — anywhere inside `Observer::open`,
`routes`, `registry`, `engine`, `admission`, `ingest`, or `sources` — stop and report it. That is
a finding about the execution path's assumptions and it matters more than the feature. Do not
work around it.

Delivering the handle *to* the chain is not below the trait method: `chain::open`/`chain::preview`
and their four callers are the routing path, and threading the handle there is the delegation
itself. What must stay untouched is the query path a router query enters through
`Observer::open(query)` — that entry takes no new argument and gains no new branch.
</objective>

    **Why the handle is borrowed, not owned.** `Router::open` receives `&dyn RouterQueries` and
    cannot store it. That makes non-retention structural rather than a rule, and it removes the
    `Arc` cycle question entirely (RESEARCH.md Q4 assumed an `Arc`-backed handle; the borrow is
    strictly stronger). It costs nothing: `OutboxSession`'s author set is fixed by its
    `RouteRequest` for the session's whole life, so it never needs to re-query. The returned
    `RouterObservation` *is* retained by the session; it holds `Arc<Registry>`, and `Registry`
    holds no routers, so there is still no cycle.

    **The open question — preview.** `ARCHITECTURE.md:1290`: "Preview never creates publication or
    relay-acquisition ownership merely because an application asks where an operation would
    currently go." An `Explicit` live query *does* create relay-acquisition ownership. So preview
    cannot be handed the same capability as `open` without contradicting that line — but the
    outbox's preview needs a warm cache read, or `preview_routes` against a fully warm cache still
    reports unresolved.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| router → engine handle | A third-party router calls into the engine. Everything it passes — the `Query`, its acquisition, its freshness, its relay set — is untrusted. |
| handle → `Observer::open` | The delegation point. Whatever crosses it runs the full production query path with full engine capability. |
